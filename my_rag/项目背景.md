# 项目背景说明：本地表结构问答助手（RAG + 结构化查询）

整理自用户与 Claude 的对话（2026-11-04）。本文档交给另一个 AI 助手阅读，目的是让它先了解背景、需求、已有结论和约束，再协助设计与开发。

## 1. 一句话概括

用户新入职一家公司，手上有一堆 Word、Excel，内容都是数据库和表的字段信息。他想做一个**本地运行、使用小模型**的“表结构问答助手”：既能按含义找表找字段，也能做精确列举、统计和表间关系梳理。同时希望把它做成求职作品，目标方向是 AI agent 开发岗位。

## 2. 用户情况与环境

- 五年 C# 后端经验，也会 Java、Python、Go。请用中文交流。
- 正在从后端开发转向 AI agent 开发方向，需要有说服力的作品。
- 当前工作目标：尽快熟悉公司的表结构，减少在工作上的耗时。工作交付优先，作品不能拖垮日常工作。
- 开发环境：个人电脑 ThinkPad E14，Intel i5 十代 CPU，预计只能靠 CPU 跑模型（是否有独立显卡、内存多大待确认）。希望全程本地运行，使用能在这台电脑上跑的小模型（几 B 参数的量化模型）。
- 实现语言未定。用户熟悉 C#、Java、Python、Go，agent 领域生态以 Python 最主流，可作为默认建议。

## 3. 对话中已形成的结论

### 3.1 概念背景

- RAG 是技术手段：回答前先检索外部资料，再让模型基于资料作答，解决模型“不知道”的问题。
- Agent 是运行方式：LLM 在循环里自己决定调用什么工具、调几次，解决模型“做不了”的问题。RAG 可以被包装成 agent 的一个工具。
- 能用确定性代码解决的，不要上 agent。升级阶梯：普通代码与接口 → 固定工作流 → 单步决策（模型只在有限选项里选）→ agent。
- 本项目遵循的原则：**不确定的部分交给模型（理解自然语言、选工具、转述结果），需要可靠的部分用确定性代码（精确列举、统计、关系）。**

### 3.2 问题一：这批 Word/Excel 适合做成 RAG 吗？

结论：适合，但取决于问题类型。

- 适合 RAG 的问题：按含义找表、找字段，查字段说明。例如“订单表的 status 字段有哪些取值”“用户手机号存在哪张表”。答案就在文档的某一段或某几行里，检索后让模型转述即可。
- 不适合单纯靠 RAG 的问题：精确列举、统计、关系梳理。例如“哪些表有 user\_id”“从订单到用户到地址要关联哪几张表”。向量检索一次只取回几个片段，容易漏；跨多处综合推理也是小模型的弱项。
- 字段表是结构化数据，直接切块做向量检索效果往往不如预期。
- 小模型风险：理解与综合能力有限，检索不准时容易答错，而且答错时语气仍然很自信；工具调用不稳定。

### 3.3 问题二：日常多问第一种，但想做到第二种，作为求职项目

结论：两个目标可以放进同一个项目，做法是**按问题类型分流**。

- 找表找字段、查含义：用 RAG（语义检索）。
- 精确列举、统计、关系梳理：不要让模型“读文档算出来”，而是先把 Word/Excel **解析成结构化数据**（例如存进 SQLite 的“表信息”“字段信息”“关系”几张表），再用确定性代码或 SQL 查询。模型只负责把自然语言翻译成该调哪个查询，并把结果用人话讲出来。
- 这个“哪部分用检索、哪部分用确定性代码、为什么”的设计，本身就是作品的亮点，比普通 RAG 演示更有说服力。

## 4. 数据库部分（重点）

### 4.1 公开示例数据库的角色

公司的库表信息属于内部资料，不能放进公开仓库，也不适合面试展示。所以作品使用**公开的示例数据库**。注意它的角色：

- 它不是让 agent 去查业务数据，而是充当“一个有几十张表的公司数据库”的**替身**。
- 从它导出 schema 元数据（表、字段、类型、主键、外键、已有的字段说明）。
- 据此用脚本**生成模拟公司风格的 Word/Excel 字段说明文档**（刻意做出不同排版：列名不统一、一个文件多个 sheet、合并单元格、中英文混杂、部分字段缺说明），模拟真实资料的混乱程度。
- 因为真实 schema 已知，可以**自动生成带标准答案的测试题**，用来评测检索召回率和工具调用正确率，例如：哪些表含某字段（精确集合）、某表的主键、两张表之间的连接路径（由外键推出）。
- agent 面对的输入仍然是 Word/Excel 文档，与真实场景一致。公司真实文档只在本地私用，同一套代码直接换数据即可。
- 可选扩展：让 agent 生成 SQL 并在示例库上执行（text-to-SQL 方向），展示更完整的 agent 能力。

### 4.2 选库原则

1. **表要足够多（几十张以上）。** 如果只有十来张表，整个 schema 几千 token 就能直接塞进上下文，根本不需要检索，项目体现不出 RAG 和分流设计的价值，也暴露不出真实难点（同义字段、命名混乱、跨 schema 关联）。
2. 有清晰的业务语义和外键关系，方便生成问题与标准答案。
3. 能在个人笔记本上轻量运行（SQLite 或 PostgreSQL 优先；SQL Server 对这台机器偏重）。
4. 许可允许公开展示。

## 5. 建议的系统结构

1. **解析层**：把 Word、Excel 统一解析成“表名、字段名、类型、说明、主外键”等结构，存入本地 SQLite（元数据库）。这是工作量最大、价值最高的一步，要处理格式不统一的问题，并保留来源（文件、sheet、行号）以便回溯。
2. **检索层**：SQLite 全文检索 + 向量检索。嵌入模型很小，CPU 完全跑得动。
3. **确定性查询层**：精确列举、统计、关系查询全部走 SQL，不经过模型推理。
4. **模型层**：小模型只做三件事：理解问题并选择工具、填参数、把结果转述成自然语言。回答里要附带来源。
5. **工具集（尽量少、参数简单）**：按语义搜表；查某张表的完整字段；按字段名反查所有包含它的表；查与某表相关联的表（基于外键，或同名字段推测，并标明是推测）。

## 6. 建议的推进顺序

1. 选库，导出 schema，生成模拟的 Word/Excel 文档和测试题。
2. 编写解析与清洗，存入 SQLite。
3. **先做不带模型的版本**（全文检索 + 筛选）。这个版本一两天就能在工作中用起来，直接满足“尽快熟悉表结构”的目标。
4. 加入向量检索，支持按含义找表找字段。
5. 接入小模型做问答和工具调用。
6. 用自动生成的测试题做评测，记录失败案例，整理成作品文档。

## 7. 约束与注意事项

- **合规**：公司文档不得进入公开仓库；本地使用前，建议先确认把公司文档放到个人电脑是否被允许。
- **工作优先**：第 1 到 3 步已能解决大部分日常需求，后面的步骤主要为作品服务，不要拖慢当前工作的交付。
- **小模型的可靠性**：工具要少而简单，关键结果要能校验；回答必须带来源；检索不到时应当回答“没找到”，不要编造。
- **模型选择**：具体用哪个模型、哪个量化版本，需要到时在这台机器上实测几个再定（该领域更新快，不要凭印象定型号）。
- 选库时核对表数量、获取方式、许可证。

## 8. 待确认的问题

- 电脑内存大小，是否有独立显卡。
- 真实文档的样貌：典型的一份表结构说明怎么排版（Word 里是表格还是段落，Excel 是否多 sheet、有无合并单元格），字段说明是否完整，有没有枚举值说明。
- 实现语言是否定为 Python。
- 公司是否允许在个人电脑上处理这些文档。
